# TracePulse

TracePulse is a Kali-hosted Bluetooth and network security monitor. The
**laptop is the monitoring console** and the **phone is the security-action
executor**. The phone can send authenticated heartbeat, lock, and unlock
requests; the laptop displays endpoint identity, link health, perimeter
status, decisions, and the audit event stream.

## Requirements

Run the laptop side on Kali Linux or another Linux system with an X11 desktop
session:

- Python 3.13 (Python 3.11-3.13 is supported; the setup script uses
  `python3.13`)
- Node.js 18 or newer and npm
- `curl`, `openssl`, and `hostname`
- A working graphical session for lock/unlock testing
- Bluetooth/BlueZ and an `hci0` adapter for RSSI proximity detection
- A phone on the same LAN for pairing

BLE is optional for initial pairing. If BlueZ is unavailable, TracePulse
continues in degraded telemetry mode; HTTPS pairing and explicit phone lock
and unlock requests still work.

## Install

Clone the repository and enter it:

```bash
git clone https://github.com/Syahmiani/Tracepulse.git
cd Tracepulse
```

Install the backend environment:

```bash
./scripts/setup-kali.sh
```

Install frontend dependencies:

```bash
cd frontend
npm install
npm run build
cd ..
```

The first setup may require:

```bash
sudo apt update
sudo apt install -y python3.13 python3.13-venv nodejs npm curl openssl
```

For Android APK builds, also install Android Studio and JDK 21:

```bash
sudo apt install -y openjdk-21-jdk
```

## Start the complete local demo

Use the integrated launcher. It starts the HTTPS backend, HTTPS Vite
frontend, certificate generation, LAN detection, health checks, and browser
opening:

```bash
./scripts/demo-workflow.sh
```

The launcher prints a URL similar to:

```text
https://192.168.0.152:5173
```

Open that URL on the **Kali laptop**. Keep the first terminal running. Press
`Ctrl+C` in that terminal to stop both services.

If the laptop has multiple network interfaces, select the correct LAN address:

```bash
TRACEPULSE_DEMO_IP=192.168.1.25 ./scripts/demo-workflow.sh
```

For a headless or manually opened browser:

```bash
TRACEPULSE_OPEN_BROWSER=false ./scripts/demo-workflow.sh
```

## Pair the phone

1. Start `./scripts/demo-workflow.sh` on Kali.
2. Open the printed HTTPS URL on the laptop.
3. Confirm the laptop shows **SCAN TO CONNECT** with a QR code.
4. Scan the QR code with the phone camera.
5. Open the TracePulse URL on the phone.
6. Accept the phone pairing request.
7. Leave the phone on the waiting screen.
8. On the laptop, accept the pending pairing request.
9. Both devices then enter their dashboards.

The QR is generated by the laptop only. It is one-time and expires. If a
challenge is rejected, do not reuse the old QR; refresh the laptop pairing
page so it creates a new offer.

The first HTTPS visit may show a self-signed certificate warning because the
certificate is generated locally for the current LAN IP. Accept it only when
you are connecting to your own Kali machine on a trusted LAN.

## Dashboard workflow

### Laptop monitoring console

The laptop dashboard shows:

- Kali and phone IP/MAC information when available
- Hostname, user, device label, and phone model
- Heartbeat age and link state
- RSSI-derived distance and the 8-meter perimeter
- Lock delay and decision-engine state
- Kali graphical session state
- Audit integrity
- Authenticated security event stream

### Phone executor

The phone dashboard provides:

- Heartbeat transport
- `LOCK NOW`, which is the only normal action that starts lock enforcement
- Authenticated unlock challenge flow
- Locked/restored notifications
- `UNPAIR`, which revokes the session on the server and refreshes both
  devices

When `UNPAIR` is pressed, the phone and laptop secure connections are severed.
The laptop returns to a new QR pairing page; the phone returns to a
**READY TO SCAN** screen and does not generate a QR.

## Configuration

The example configuration is at
[`config/tracepulse.example/toml`](config/tracepulse.example/toml).
For a normal demo, environment variables are set by
[`scripts/demo-workflow.sh`](scripts/demo-workflow.sh).

Useful overrides:

```bash
export TRACEPULSE_DEMO_IP=192.168.1.25
export TRACEPULSE_PROXIMITY_DISTANCE_METERS=8
export TRACEPULSE_PROXIMITY_LOCK_DELAY_SECONDS=5
export TRACEPULSE_BLE_ADAPTER=hci0
```

Never commit `config/tls/server.key`, `config/tls/ca.key`, `.env`, database
files, or runtime logs. The repository ignores those files. Generate fresh
local certificates with:

```bash
./scripts/generate-certificates.sh
```

## Manual service start

The integrated launcher is recommended. For troubleshooting, start the
backend and frontend separately in two terminals.

Terminal 1:

```bash
export TRACEPULSE_SERVICE_URL=https://192.168.1.25:8443/
export TRACEPULSE_CERT_IP=192.168.1.25
export TRACEPULSE_TLS_CERT="$PWD/config/tls/server.crt"
export TRACEPULSE_TLS_KEY="$PWD/config/tls/server.key"
./scripts/generate-certificates.sh
./scripts/start-dev.sh
```

Terminal 2:

```bash
cd frontend
VITE_DEV_HTTPS=true \
VITE_DEV_TLS_CERT="$PWD/../config/tls/server.crt" \
VITE_DEV_TLS_KEY="$PWD/../config/tls/server.key" \
npm run dev -- --host 0.0.0.0
```

## Troubleshooting

### The QR is missing

Make sure the laptop URL is open over `https://`, not `http://`, and that
port `8443` is reachable locally. Reload the laptop page to create a fresh
pairing offer.

### Pairing challenge rejected

The QR may be expired or already used. Reload the laptop pairing page and scan
the newly displayed QR. Do not scan a QR from an earlier browser tab.

### The phone is waiting forever

The laptop must explicitly accept the pending pairing request. The phone does
not enter its dashboard immediately after phone acceptance.

### The phone cannot reach the laptop

Verify both devices are on the same LAN, use the LAN IP printed by the
launcher, and allow inbound TCP ports `5173` and `8443` in the Kali firewall.

### BLE is degraded

Check that BlueZ is running and that `hci0` exists:

```bash
systemctl status bluetooth
bluetoothctl list
```

BLE degradation does not prevent HTTPS pairing or explicit manual lock and
unlock testing.

### Lock/unlock does not affect the desktop

Run the demo from the active Kali graphical session. XFCE uses
`xfce4-screensaver-command`; other desktop environments may require their own
locker integration. Confirm the phone secure channel says **CONNECTED**.

## Security notes

TracePulse uses HTTPS, X25519 key agreement, HKDF-derived session keys,
HMAC-authenticated envelopes, sequence numbers, nonces, replay protection,
and Ed25519 unlock assertions. The generated development TLS certificate is
self-signed and intended for trusted local-network testing, not public
internet deployment.

See [`SECURITY.md`](SECURITY.md) and
[`THREAT_MODEL.md`](THREAT_MODEL.md) for the security policy and threat model.
